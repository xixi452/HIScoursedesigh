## 二、范围取舍决策记录

### 2.1 冲突原文

- PPT 第 10 页 A 线：挂号 + 门诊医生工作站子集 + 划价收费 + 门诊药房（4 个）。
- 同页规矩一：分系统组合不超过 3 个。

### 2.2 备选方案

| 方案 | 组合 | 优点 | 风险 | 结论 |
|---|---|---|---|---|
| A | 挂号 + 医生站 + 药房（含划价收费） | 3 个分系统；闭环完整；收费与发药在同一窗口，事务边界清晰 | 与规范“划价收费”单列不完全一致 | **推荐，待老师确认** |
| B | 挂号 + 医生站 + 划价收费（含发药） | 3 个分系统；收费单列 | 药房库存/效期管理被弱化，发药像收费的附属 | 备选 |
| C | 挂号 + 医生站 + 划价收费 + 药房 | 最贴规范 | 违反“最多 3 个”，5 周做不完 | 不采用 |

### 2.3 建议口径（答辩用）

> “A 线原始描述有 4 个分系统，但课程规矩最多 3 个。我们把‘划价收费’作为门诊药房模块里的收费窗口实现，报 3 个分系统：挂号、门诊医生工作站、门诊药房。闭环仍然是挂号→就诊→开方→收费→发药，没有少任何一步。”

## 三、10 个核心实体人工核对单

> 用法：让 AI 生成 SQL 后，逐表对照。以下“打回条件”满足任意一条，就退回重写，不允许“先跑起来再说”。

### 3.1 患者 `patients`

- [ ] 有 `patient_no`、`name`、`gender`、`birth_date`、`phone`、`status`。
- [ ] 身份证只存 `id_card_masked`、`id_card_hash`、`id_card_last4`，**没有** `id_card` 明文列。
- [ ] `id_card_hash` 有唯一约束。
- [ ] 脱敏串满足“前 6 + 8 星号 + 后 4”，长度 18。
- [ ] 手机号展示脱敏（`138****5678`）。

**打回条件**：出现明文身份证列；只有脱敏串没有哈希（无法查重）；哈希不唯一。

### 3.2 科室 `departments`

- [ ] 有 `dept_code`、`name`、`location`、`intro`、`status`。
- [ ] `dept_code` 唯一。
- [ ] 停用科室不能新挂号（应用层校验）。

**打回条件**：只有名称，没有位置/简介/状态；停用后仍可挂号。

### 3.3 医生 `doctors`

- [ ] 有 `doctor_no`、`name`、`title`、`dept_id`、`specialty`、`status`。
- [ ] `dept_id` 外键指向科室。
- [ ] 医生“停诊/离岗”与排班“停诊”区分：医生状态影响能否排班，排班状态影响能否挂号。

**打回条件**：没有职称/专长/状态；医生不属于任何科室。

### 3.4 排班号源 `schedules`（挂号的“库存”）

- [ ] 有 `doctor_id`、`dept_id`、`work_date`、`time_slot`、`reg_level`、`fee_cents`。
- [ ] 有 `total_count`、`remaining_count`，且 `0 <= remaining_count <= total_count`。
- [ ] 有 `status`（正常/停诊/满号）与 `version`（乐观锁）。
- [ ] `(doctor_id, work_date, time_slot, reg_level)` 唯一。
- [ ] 挂号时条件更新 `remaining_count > 0`，不是先查再减。

**打回条件**：只有总量没有剩余量；没有时段/号别/挂号费；剩余量可为负；同一医生同日同时段可重复排班；没有状态。

### 3.5 挂号单 `reg_orders`

- [ ] 有 `reg_no`、`patient_id`、`doctor_id`、`dept_id`、`schedule_id`、`reg_time`。
- [ ] 有 `queue_no`、`fee_cents`、`status`、`operator_id`、`cancel_reason`。
- [ ] `(schedule_id, queue_no)` 唯一。
- [ ] 状态覆盖候诊/就诊/完成/退号/取消。

**打回条件**：没有 `schedule_id`（无法回滚号源）；没有 `queue_no` 或排队号不唯一；没有状态/操作人。

### 3.6 处方 `prescriptions`

- [ ] 有 `prescription_no`、`reg_id`、`patient_id`、`doctor_id`。
- [ ] 有 `diagnosis`、`prescribe_time`、`total_amount_cents`、`status`。
- [ ] 状态覆盖草稿/待收费/已收费/已发药/已退费/已退药/作废。
- [ ] 处方必须关联挂号单；一张挂号单可多张处方。

**打回条件**：没有诊断/开方时间/总额；状态只有“已开/已发”；处方不关联挂号单。

### 3.7 处方明细 `prescription_items`

- [ ] 有 `prescription_id`、`drug_id`、`quantity`、`unit_price_cents`、`amount_cents`。
- [ ] `amount_cents = quantity * unit_price_cents`。
- [ ] 有 `dosage`、`frequency`、`usage_text`、`days`。
- [ ] 有 `dispensed_quantity`（0 到 quantity）与 `status`。
- [ ] 单价是开方时快照，药品调价不影响已开处方。

**打回条件**：没有单价快照/金额；没有用法/频次/天数；没有已发数量；金额用浮点。

### 3.8 药品 `drugs`

- [ ] 有 `drug_code`、`generic_name`、`trade_name`、`spec`、`dosage_form`、`unit`。
- [ ] 有 `price_cents`、`insurance_type`、`status`。
- [ ] 停用药品不能开方，但历史处方仍可查看。

**打回条件**：只有名称和价格；没有规格/剂型/单位/医保类别/状态。

### 3.9 药品库存 `drug_stocks`

- [ ] 有 `drug_id`、`batch_no`、`production_date`、`expiry_date`、`quantity`、`location`。
- [ ] 有 `status`（正常/冻结/过期/召回）与 `version`。
- [ ] `(drug_id, batch_no)` 唯一。
- [ ] 发药按 FEFO（效期升序），过期/冻结/召回不可发。
- [ ] 库存不能为负；退药回补原批次，并同步把收费单置为已退费。

**打回条件**：只有药品+数量，没有批次/效期/状态；发药扣总库存不扣批次；过期批次仍可发；库存可为负。

### 3.10 收费单 `bills`

- [ ] 有 `bill_no`、`bill_type`、`reg_id`、`prescription_id`、`patient_id`。
- [ ] 有 `total_amount_cents`、`payment_method`、`cashier_id`、`paid_at`、`status`。
- [ ] 有 `request_id` 唯一（幂等），`invoice_no` 可空。
- [ ] 挂号费只关联 `reg_id`，药品费只关联 `prescription_id`（XOR）。
- [ ] 收费后处方状态同步“已收费”；退费/退药后收费单“已退费”。

**打回条件**：没有收费员/时间/状态；没有幂等键；一张单同时挂挂号单和处方；金额用浮点；收费与处方状态不在同一事务。

## 四、身份证脱敏规则确认单

- [ ] 展示格式：前 6 位 + 8 个星号 + 后 4 位，例如 `110101********1234`。
- [ ] 存储：`id_card_masked` + `id_card_hash` + `id_card_last4`，不存明文。
- [ ] 哈希：`SHA-256(pepper + 规范化身份证号)`，pepper 放环境变量，不进 Git。
- [ ] 查询：按哈希精确匹配，不做明文模糊查询。
- [ ] 日志/导出/错误提示：一律脱敏。
- [ ] 真实项目升级：AES-256-GCM 加密 + KMS，授权+审计才能解密。
- [ ] 演示数据：全部虚构，不使用真实患者信息。

**红线**：数据库、日志、localStorage、URL、错误堆栈、Git 仓库、答辩截图，出现完整身份证即视为事故。

## 五、AI 使用边界

### 5.1 AI 可以干的（本组已用）

| 任务 | AI 产出 | 人工如何处理 |
|---|---|---|
| 从规范条文提取功能点 | 功能点初稿、用户故事、验收标准 | 人工删减、合并、定“实现/不实现” |
| 生成 ER 图 | Mermaid `erDiagram` 代码 | 人工核对 10 实体、关系基数、XOR |
| 生成建表 SQL | SQLite DDL、CHECK、索引、视图 | 人工逐表核对字段、约束、金额单位 |
| 生成测试用例 | 正常/边界/并发/越权用例 | 人工补业务反例、脱敏检查 |
| 解释 SQL/报错 | 逐段解释、改写建议 | 人工判断是否接受，不盲信 |

### 5.2 AI 不能替你干的

- 决定“做什么/不做什么”以及理由。
- 对 10 个实体是否齐全、字段是否够用负责。
- 决定身份证脱敏/加密规则。
- 决定事务边界与并发方案。
- 在答辩时解释“为什么这样取舍”。

### 5.3 AI 常见错误清单（审查时逐条对照）

1. 只建业务表，不建用户/角色/权限/审计日志。
2. 金额用 `REAL/FLOAT`，出现 `0.1+0.2` 精度问题。
3. 号源只存“总量”，不存“剩余量”，挂号时临时算。
4. 药品库存只存“药品+数量”，不存批次、效期、状态。
5. 处方明细不存单价快照，收费时读当前药品价，导致历史处方变价。
6. 收费单没有收费员、时间、状态、幂等键。
7. 身份证存明文，或只存脱敏串没有哈希，无法查重。
8. 挂号用“先查剩余量，再减一”，并发超卖。
9. 发药只扣总库存，不按批次/FEFO，过期药也能发。
10. 状态字段没有 CHECK，出现“已收费又已退费”的脏数据。
11. 退号/退费/退药没有反向流水，账对不上。
12. 权限只在前端隐藏菜单，后端接口不校验。

## 六、可复用 AI 提示词

### 6.1 从规范条文提取功能点

```text
你是医院信息系统需求分析员。下面是我选定的《医院信息系统基本功能规范》条文（粘贴原文）：

【粘贴规范原文】

请只基于上述条文提取功能点，不要添加条文没有的功能。输出 Markdown 表格：
编号 | 分系统 | 功能点 | 条文依据（原文摘录不超过30字） | 一句话说明 | 建议优先级(P0/P1/P2)

要求：
1. 区分“分系统—功能点—子功能”，不要把子功能抬成独立分系统。
2. 条文含糊或缺失的地方，标注“需人工确认”，不要自行补全。
3. 不要写技术实现方案，不要写代码。
4. 最后列出“你认为条文没写清、需要问老师的问题”。
```

### 6.2 让 AI 做“砍功能”的项目经理

```text
你是严格的项目经理，负责一个 5 周、2-3 人的课程项目。约束：
- 只报 3 个分系统：门诊挂号、门诊医生工作站、门诊药房（含划价收费）。
- 必须跑通闭环：挂号扣号源 → 就诊 → 开方 → 收费 → 发药扣库存。
- MVP 不做：预约、医保、在线支付、LIS/PACS、电子病历归档、盘点调拨、麻精药品。
- 必须有登录/角色/权限、事务、身份证脱敏。

下面是候选功能点清单：
【粘贴功能点】

请逐条给出：实现 / 不实现 / 实现（简化），并说明理由。理由只能落在以下五类：
闭环必需、合规必需、依赖外部系统、规则/知识库复杂、超出 3 个分系统。
不要讨好我，优先砍功能；如果某条你认为必须做但我漏了，单独列“建议补做”。
```

### 6.3 生成 ER 图（Mermaid）

```text
你是数据库架构师。请为“A 门诊线”生成 Mermaid erDiagram，必须包含 10 个核心实体：
患者、科室、医生、排班号源、挂号单、处方、处方明细、药品、药品库存、收费单。
另加支撑实体：用户、角色、权限、角色权限、发药记录、审计日志。

业务规则：
1. 排班号源是挂号的“库存”，必须有 total_count、remaining_count、time_slot、reg_level、fee_cents、status、version。
2. 药品库存必须按批次，有 batch_no、production_date、expiry_date、quantity、status、version。
3. 收费单必须能区分挂号费/药品费，reg_id 与 prescription_id 二选一。
4. 处方明细必须有单价快照、金额、用法、频次、天数、已发数量、状态。
5. 发药记录要能追溯到处方明细和库存批次。

输出要求：
- 只输出 Mermaid 代码和“关系说明表”。
- 每个实体列出关键字段与 PK/FK/UK。
- 最后给一份“AI 自检清单”：你最容易漏的字段是什么，为什么。
```

### 6.4 生成 SQLite 建表 SQL

```text
你是 SQLite 数据库架构师。基于上面的 ER 图生成可直接执行的 DDL。

硬性要求：
1. 开启 foreign_keys；金额全部用 INTEGER 存“分”，禁止 REAL/FLOAT。
2. 所有状态字段用 CHECK 限制枚举；所有唯一业务键加 UNIQUE。
3. 排班号源：remaining_count 必须在 0..total_count；同一医生+日期+时段+号别唯一。
4. 药品库存：同一药品+批次唯一；quantity >= 0；expiry_date 必填。
5. 处方明细：amount_cents = quantity * unit_price_cents。
6. 收费单：bill_type=挂号费 时 reg_id 非空且 prescription_id 为空；bill_type=药品费 时反之；request_id 唯一。
7. 患者：不建身份证明文列，只建 id_card_masked、id_card_hash（唯一）、id_card_last4。
8. 建立必要索引和 2-3 个查询视图（可挂号源、库存预警、待收费处方）。
9. 不要写注释，不要写种子数据。

输出后附：
- 每个 CHECK 约束的目的（一句话）。
- 你认为最容易在并发下出问题的地方，以及对应的事务写法（BEGIN IMMEDIATE + 条件更新）。
```

### 6.5 让 AI 做“对抗性审查”

```text
你是验收专家，专门挑漏。下面是一份 AI 生成的 SQLite DDL：
【粘贴 SQL】

请逐表审查，重点找：
1. 号源/库存是否可能为负或超卖；是否有条件更新和唯一约束。
2. 药品库存是否漏批次、效期、状态；过期/冻结是否还能发药。
3. 处方明细是否漏单价快照、金额、用法、频次、天数、已发数量。
4. 收费单是否漏收费员、时间、状态、幂等键；挂号费/药品费是否可能同时挂错。
5. 患者身份证是否存明文；是否只脱敏没哈希。
6. 退号/退费/退药是否有反向流水和状态回滚。
7. 权限是否只在前端；审计日志是否覆盖关键操作。

输出表格：问题 | 所在表/字段 | 为什么是线上事故 | 最小修法。
不要客气，不要假设“应该没问题”。
```

### 6.6 生成验收测试用例

```text
你是测试工程师。根据以下验收标准生成测试用例：
【粘贴功能点清单的验收标准】

要求覆盖：
- 正常主流程（挂号→接诊→开方→收费→发药）。
- 边界：号源=0、库存=0、库存不足整单回滚、金额=0、数量=0。
- 并发：最后 1 个号源 20 人抢；同一处方重复点击收费；同一批次并发发药。
- 越权：挂号员开方、医生收费、药师退费、未登录访问。
- 合规：页面/日志/导出无完整身份证；重复身份证查重。
输出：用例编号 | 前置条件 | 步骤 | 预期结果 | 类型。
```

## 八、待问老师的问题

1. A 线 4 个分系统与“最多 3 个”冲突，按“药房含划价收费”报 3 个是否认可？
2. 挂号费是否必须在挂号时收？能否并入处方收费，减少一次收费动作？
